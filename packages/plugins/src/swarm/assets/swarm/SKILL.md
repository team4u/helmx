# Swarm Multi-Agent Peer Collaboration

Use `builtin:swarm` for horizontal, adaptive peer collaboration on a single shared `#seq` blackboard when roles need to inspect each other's progress, run multi-round write/review cycles, or evolve the team shape as findings emerge.

## 1. When to Use, When Not to Use & How to Activate

- **Use `swarm` when**:
  - Multiple non-overlapping code slices or deep investigation tracks benefit from running concurrently **and** coordinating findings or cross-module contracts on a shared board.
  - Implementation slices need iterative **writer <-> read-only verifier** handoff/review/fix loops before coordinator merge.
  - The squad shape cannot be scripted up front—you may need to recruit extra specialists, steer/abort a stuck peer, or switch a worker's model mid-task while keeping the user conversation responsive.
- **Do NOT open a swarm group when**:
  - **Small or tightly sequential work**: handle it directly in the current conversation.
  - **One isolated subtask** (single lookup, one blind review, one bounded fix): use `subagent` (when enabled) instead of creating a group.
  - **Fixed, repeatable pipelines** (fan-out batch audits without peer cross-talk, staged pipelines, strict `gate`/schema checkpoints, saved/scheduled runs, or orchestration inside a child/automated session): use `SubagentWorkflow` (`workflow` skill, when enabled).
- **Activation & eligibility (top-level human conversations only)**:
  - **Explicit `/skill:swarm <task>` entry**: When the user sends `/skill:swarm <task>` (or `/skill:swarm`) in a top-level human conversation, `builtin:swarm` automatically activates (or reuses) a collaboration group on that conversation and unlocks the `swarm_*` tools in the same turn.
  - **Model-initiated or natural-language activation**: When in a normal top-level conversation you judge that the task matches the criteria above (or the user asks for multi-agent collaboration in natural language) and no active group exists yet, call `swarm_create_group` first to open the collaboration board on the current conversation, then recruit and schedule peer workers on the following step.
  - **Top-level only**: Collaboration groups can only be started on top-level human conversations—never from a worker, child, or automated sub-conversation.
  - **Tools vs CLI**: Inside Agent turns, always drive `builtin:swarm` with the direct `swarm_*` tools (`swarm_create_group`, `swarm_update_group`, `swarm_dispatch_worker`, `swarm_board_post`, `swarm_board_read`, `swarm_board_status`, `swarm_inspect_worker`, `swarm_abort_worker`, `swarm_switch_worker_model`, `swarm_archive_worker`, `swarm_close_group`) and `run_action({ actionId: "builtin:swarm.list_groups", input: { status?, coordinatorConversationId? } })` to list active or closed swarm groups across conversations — do not shell out to `helmx swarm` via `bash`. Use `swarm_switch_worker_model` with optional `effort` and `prompt` to swap an idle/failed worker's model (or `tier/<id>`) and wake it in one step. (CLI for terminals/scripts: `helmx swarm <subcommand>`, e.g., `helmx swarm list-groups`, `helmx swarm create-group`, `helmx swarm dispatch-worker`, `helmx swarm board-status`, `helmx swarm close-group`.)

## 2. Coordinator Rule: Do Not Do the Work

- The coordinator conversation (`swarm-coordinator`) decomposes work, dispatches named peer roles (`swarm_dispatch_worker`), resolves cross-slice blockers, and performs final branch merging and group closure.
- Do not write business code or sit inside long blocking builds/tests directly in an active coordinator session; delegate implementation, testing, and review fixes to workers so blackboard scheduling and user replies stay responsive. Quick read-only lookups (`read`, `rg`, `git status`, `git diff`) to size and split the work are fine.

## 3. Dynamic Role Sizing, Permissions, and Workspace Isolation

- Dynamically decide the squad shape on the spot from the task's complexity and file boundaries—never stamp out fixed role-name templates or fixed team sizes.
- When recruiting each worker via `swarm_dispatch_worker`, specify:
  - **`name` & `prompt`**: A unique lowercase member name (avoiding reserved `coordinator`, `all`, `system`) and a focused task prompt with explicit, non-overlapping file ownership. For `isolation: 'worktree'` workers, do not invent or hardcode a worktree path in the brief—`builtin:worktree` allocates the managed worktree and injects `<worktree_context>` automatically.
  - **`access` (`readwrite` vs `readonly`)**: Use `readwrite` for implementation slices; use `readonly` for read-only research or cross-verification (verifiers run builds, typechecks, lints, and tests via `bash`, inspect diffs, and post review outcomes via `swarm_board_post` without modifying files; `readonly` is a task convention rather than a hard tool sandbox—use `isolation: 'worktree'` to isolate concurrent writes).
  - **`isolation` (`worktree` vs `inherit`)**: Code-editing and integration members must use `isolation: 'worktree'` so `builtin:worktree` manages allocation, holds, `<worktree_context>`, and `worktreeSnapshot`—**never** run manual `git worktree add` and pass `cwd` to bypass `isolation: 'worktree'`. Read-only researchers or cross-verifiers may use `isolation: 'inherit'` with `access: 'readonly'`.
  - **Optional overrides**: Set `profileId`, `nodeId` + `cwd`, `model`, `effort`, or `forkFrom` / `forkEntryId` per worker when specialized personas, remote compute nodes, or heterogeneous models help. `nodeId` overrides the Profile/coordinator node (explicit `"local"` switches back to the Hub host; remote nodes require an explicit `cwd` or a compatible Profile `cwd`, and concurrent code-editing workers whose worktree branches will be merged locally by the coordinator should share the same node).

## 4. Event-Driven Waiting, `#seq` Handoffs, Orthogonal `wake`, and Two-Mode Close

- **Async dispatch & no polling**: `swarm_dispatch_worker` starts each worker asynchronously in the background and returns immediately. After dispatching workers or sending a board update, briefly report the plan to the user and end your turn—never `sleep` or loop on `swarm_board_status` / `swarm_board_read` / `swarm_inspect_worker` to wait for results.
- **Automatic `<swarm_board_report>` delivery & on-demand inspection**:
  - The coordinator is woken automatically with `<swarm_board_report>` on: (1) any `blocker` (including worker turn failure) or group-wide `[stall]` (immediately, regardless of `to` or `wake`); (2) any non-`done` post whose targets include `coordinator` with `wake: true` (`handoff` / `review` / `brief` / explicit `comment`), which flushes immediately even if the sender continues working in the same turn or also addresses other members; (3) `done` posts whose targets include `coordinator` with `wake: true`, which flush as soon as that sender's current turn settles without waiting for slower peers—you can start reviewing or integrating completed slices immediately while never closing the group while `activeWorkingMembers` is non-empty (if an earlier report showed non-empty `activeWorkingMembers` and remaining workers later finish passively, an idle catch-up report arrives automatically once all workers are idle).
  - The coordinator is **not** woken for internal peer-to-peer handoffs (`writer -> verifier`), passive `comment` posts (`wake: false`), intentional `swarm_abort_worker` stops, or while a worker is still `working` or `blocked` waiting for human approval.
  - Call `swarm_board_status`, `swarm_board_read`, or `swarm_inspect_worker` **on demand** (single read): after receiving a `<swarm_board_report>` to pull `#seq` context, when the user asks for live status, before merging/closing, or when a worker appears stuck or `blocked` awaiting approval and needs intervention.
- **Zero copy-paste `#seq` pointers**: Publish progress and handoffs via `swarm_board_post` using `refs: [seq]` and `#seq` in the body instead of copying diffs, logs, or long reports across turns. When a `worktree`-isolated member posts `kind: 'handoff'` or `kind: 'done'`, the board automatically attaches a `worktreeSnapshot` (`worktreeId`, `branch`, `commitsAhead`, `dirtyCount`, `changedFilesPreview`) so peers can inspect diffs directly from that worktree.
- **Orthogonal `wake` doorbell**: `to`/`@` only specifies addressing while `wake: true` is the handoff doorbell—every woken target pays a model turn (busy targets receive coalesced wakeups when their current turn settles), so set `wake: true` only for actors who must act next. On peer handoffs (e.g. writer -> verifier or verifier -> writer), wake only the next responsible actor; use `handoff` or `review` when requesting mid-flight coordinator approval or decisions while continuing work in the same turn; reserve `kind: 'done'` (`to: ['coordinator']`, default `wake: true`) for finishing a member's current turn and delivering its slice; use `kind: 'comment'` (`wake: false` by default) for passive notes, and end turns silently instead of posting empty acknowledgments ("ack", "thanks", "received").
- **Two-mode close (`swarm_close_group`)**: Never close the group while `activeWorkingMembers` is non-empty. When integrating multiple `worktree` writer slices, prefer dispatching an `isolation: 'worktree'` integration worker to merge the `helmx/spawn-*` branches + target branch and run full verification (keeping the coordinator unblocked), then merge that verified integration branch onto the target branch and call `swarm_close_group()` so all managed worktrees clean up automatically; or call `swarm_close_group({ keepWorktree: true })` to release worktree holds and preserve modified branches in `retainedWorktrees` for subsequent merging and cleanup. On nodes without process-usage scanning (e.g. Windows/macOS), clean worktrees release holds and remain listed in `uncleanedWorktrees` unless `allowUnverifiedUsage: true` is passed after confirming no processes use those directories. `force: true` closes past the uncommitted/unmerged worktree guard (discarding such content); occupancy, ownership and locked checks still refuse.
